# 手機清點與例外紅包

## 使用流程

登入後切換「紅包清點」，會連線載入每一包已收件紅包。可依袋上的賓客編號、E 編號、姓名或紅包署名搜尋，並切換待清點、待核對、已清點或全部清單。清單與總額是上次載入狀態；另一支手機的修改需按重新載入取得。

一般清點：選紅包，核對收件人員、時間與袋上編號，填署名、金額及備註，按「確認清點」並確認摘要。Sheet 確認成功才顯示完成與下一包。署名預填賓客姓名，可依袋子修改；未知金額留白，零元需明確填 0。金額接受非負數，最多九位整數與兩位小數。

已清點資料仍可開啟更正，但須填更正原因。保留原始收件人員與時間，記錄最新清點人員、時間及 GiftAudit 中的前後值、原因。

## 例外狀況

- 同一賓客第二包：使用「例外狀況／新增一包」，選多包並填賓客編號，會新增獨立紅包，不覆蓋第一包；第一包須已完成中央收件同步。
- 名單外送禮人：新增例外紅包，賓客編號留白，填紅包署名及金額。
- 署名不同／代送：直接在原紅包的清點表單選對應類型、改署名並寫備註；只有確實多一個實體袋子才新增一包。
- 無法確認送禮人或金額：填已知資訊與待核對原因，按「記錄為待核對」。未知金額保持空白，這包不算入已清點總額。稍後可在待核對清單補齊並確認；未綁定賓客者可補上賓客編號。

新增例外紅包成功後，系統顯示 E001 等獨立編號，請立即寫在實體袋上。每次新增一個編號；逾時重試沿用同筆紀錄與編號。待核對袋子請集中放置以便後續處理。

接待畫面上的「清點待核對」代表這包的清點仍有疑問；本機收件佇列的「待核對」則代表收件撞單，兩者不可互相當作已處理。

## 斷網、重試與多人操作

清點需要連線確認。輸入中的草稿與已送出待確認請求存在本分頁 sessionStorage，不包含 PIN／token；重新整理同分頁會還原。關閉分頁可能失去草稿，因此逾時時保留分頁，按「確認上次儲存結果／重試」，不要另建第二包。

待確認期間鎖住該次輸入，重試沿用相同內容、原操作人員、帳本網址與請求編號。過期時可展開設定重新登入後重試。儲存空間不可用則不送出清點。

兩支手機同時編輯同一包時，先儲存者成功；後送出的舊版本回覆衝突，保留草稿。返回清單、重新載入並核對，再重新選取與填寫。背景收件同步與清點共用寫入鎖，但一般接待仍維持原離線收件方式。

直接在 Sheet 編輯不受 Apps Script 鎖限制。清點期間不要在 Sheet 同時改同一筆，也不要刪列或排序；程式會在寫入前再次核對資料，但 Sheets 不提供跨表交易，不能保證阻擋最後瞬間的人工編輯。

## 帳本與復原機制

Gifts 既有十五欄後追加「紅包編號、例外類型」，原資料位置不變。setupSheet 只在這兩個標題位置為空白時補入；若已有自訂欄會停止，需先備份並把自訂欄移到標準欄位之後。新增「待核對」狀態與 GiftDashboard 待核對包數。

清點 API 先把完整前後值、操作人員、原因與請求指紋寫到 GiftAudit 的 COUNT_PENDING，再寫 Gifts，最後將該事件標為 COUNT_APPLIED。途中失敗後相同請求可續做；已完成請求重送只回覆目前紀錄，不重新覆蓋後續更正。這些紀錄同時用於安全重試，請勿刪除或直接修改。

若待確認操作遇到人工改表，API 回覆 RECOVERY_CONFLICT 並停止覆蓋。管理者需先備份、比對 GiftAudit 的 before／after 與實體紅包，在 Gifts 以原收件ID保留一筆核對後的紀錄，另留人工處理說明。確認完成後才可將對應的 COUNT_PENDING 改為 COUNT_APPLIED（保留原 before／after 與請求指紋），讓原手機重試取得目前已核對的紀錄。這是人工故障復原，不應由現場人員反覆按新增或任意解除。

## 部署與驗收

1. 備份 Sheet，暫停寫入操作。
2. 更新 Code.gs、GiftRegister.gs，新增 CountGifts.gs。
3. 執行 setupSheet，確認 Gifts 尾端新欄位與待核對狀態。
4. 更新現有 Web App 的部署版本，保持原 URL，再更新 GitHub Pages 前端並重新登入。
5. 使用測試紅包驗收：一般清點、零元／空白、更正原因、署名不同、第二包、名單外、未知送禮人待核對及後續補齊、兩人同包衝突、斷網與逾時後重試、重整分頁還原。

本機測試涵蓋 API 驗證、衝突、寫入各階段故障復原及手機操作事件；不代表正式 Apps Script／實際手機畫面已驗收。
