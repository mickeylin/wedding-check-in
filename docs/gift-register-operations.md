# 禮金簿操作與部署

## 初始化與升級

先備份 Sheet。Apps Script 需要同時放入根目錄的 `Code.gs`、`GiftRegister.gs` 與 `CountGifts.gs`。在指令碼屬性設定 `API_PIN` 與 `SPREADSHEET_ID`，時區使用 `Asia/Taipei`。勿把 PIN 寫入公開程式碼。

執行 `setupSheet`：Guests 標準欄位改為「賓客ID、顯示姓名、新郎/新娘方、桌號、備註」。遷移前會複製完整舊表為隱藏的 `Guests_Archive_時間戳`，再依標題搬移資料；預計人數、實到人數、報到狀態、操作人員、報到時間從主檔移除，自訂欄位的值保留於標準欄位後方。原始格式與公式可從封存副本恢復。重跑不會重複遷移已符合格式的主檔。

舊 ScanLog 與 Dashboard 會改名為含 Archive 與時間戳的封存表並隱藏。新版不再建立或讀寫這兩張表；Gifts、GiftAudit、GiftDashboard 繼續使用。Gifts 欄位若不符合預期順序則停止。升級請安排在暫停接待時：更新 Code.gs，執行 setupSheet，更新 Web App 部署版本，最後重新登入下載名單；不要在舊部署仍接待時搬動 Guests 欄位。

如需回復，先停止接待，取消隱藏封存副本，將目前 Guests 改名保留，再把備份改名為 Guests，並回復對應舊版 Code.gs 的部署。Gifts 的禮金收件資料不需回復或覆蓋。

名單編號若需補齊可執行 `generateGuestIds`，會避開已使用的編號。正式名單匯入格式另行確認，勿直接整段貼上來源 CSV 覆蓋 Guests。

由一位管理者執行 `installGiftEditTrigger` 並完成授權，安裝 `auditGiftEdit` 的可安裝編輯觸發器。同一帳號重跑不會重複安裝；不要由兩位管理者各安裝一份。程式/API 寫入不觸發 Sheet 編輯事件，收件與撤銷資訊直接保留在 Gifts 原始列。

更新 Web App 部署版本（執行身分為擁有者、允許現場裝置存取），接著更新 GitHub Pages 的 `/docs`。兩支手機重新整理、填 API URL、工作人員姓名與 PIN 後儲存。舊前端呼叫 checkin 會被拒絕，需重新整理新版。

## 手機接待

首次使用展開「登入與設定」，填網址、人員與 PIN，按「登入並更新名單」。成功後設定會自動收合；需重新登入或下載 Sheet 最新名單時再次展開。姓名與網址保留，PIN 不保存。頁首顯示登入人員與同步狀態。

賓客資訊只呈現在同一張結果卡：姓名、大字桌號與賓客編號、紅包狀態，接著是「收到紅包」與「只查桌號／下一位」。撤銷採次要樣式且仍需確認；耗時資訊收合在按鈕下方。相機區只在啟動掃描時展開。同步摘要常駐、詳細紀錄與最近操作預設收合；待核對或儲存異常會自動展開同步紀錄。

1. 掃 QR、輸入賓客編號或以姓名／分類查找。分類中的男方朋友、女方朋友均包含共同朋友。
2. 查看姓名、桌號、紅包狀態。只查桌號直接按「下一位」，不寫入到場或收件資料。
3. 收到紅包後按「收到紅包」。看到「已保存在這支手機」即可在紅包寫上畫面上的賓客編號並處理下一位，不必等待 Apps Script。
4. 主畫面的「紅包同步」會顯示待同步、同步中、失敗重試、待核對與已同步。只有「已同步」代表資料已進入 Google Sheet；離開現場前必須清空待同步與待核對數量。
5. 已收件或已排入本機佇列者不會出現再次收件按鈕。已同步且尚未填金額／清點的收件可按「撤銷誤收件」，再次確認後撤銷；撤銷仍需連線即時確認。
6. 每次操作完成按「下一位」。掃描流程會恢復相機，查找流程可繼續搜尋。

兩支手機同時收同一賓客，一般流程只建立一筆有效收件。後送到伺服器的手機會顯示「待核對」；先把該實體紅包放入待核對區，到 Gifts 確認後再按「已核對，解除警示」。解除警示只處理手機提示，不修改 Sheet。撤銷使用原收件ID，舊畫面不能撤銷之後重新建立的收件。

待同步資料保存在該手機的瀏覽器，不包含 PIN 或 session token。若工作階段過期，使用原收件人員名稱重新輸入 PIN，按「立即重試」；不可改用另一位人員登入後代為同步，否則 Sheet 的收件人員會不正確。婚宴結束且所有紀錄均已同步／核對後，可按「清除完成紀錄」移除手機上的收件顯示資料。

## 手機清點

切換「紅包清點」，依賓客編號或 E 編號搜尋、選紅包、填署名與金額、確認儲存。畫面顯示已保存在手機後會立即回清單，可繼續其他包；清點同步區顯示「已同步」才代表資料進入 Sheet。同一包待同步時會鎖定，逾時沿用同一請求編號，單次 API 最多等待 20 秒。已清點的更正需填原因；例外新增、待核對及重試方式見[手機清點說明](mobile-gift-counting.md)。

升級需更新三個 Apps Script 檔案並執行 setupSheet，在 Gifts 十五個既有欄位後補「紅包編號、例外類型」，新增待核對狀態。若尾端標準欄位位置有自訂欄，需先備份並移至標準欄位之後，再重跑。更新 Web App 部署後才啟用新版前端。

## Google Sheet 管理與人工清點

在 Gifts 用賓客ID找實體紅包對應列。每列保留一個收件紀錄；撤銷不刪列，重新收件另增新列。內部收件ID不用寫到紅包上。

| 欄位 | 用法 |
| --- | --- |
| 收件ID、收件請求ID、撤銷請求ID | 系統追蹤用，勿修改或複製到新列 |
| 賓客ID、顯示姓名 | 對應主要送禮人 |
| 紅包署名 | 依紅包補登，允許與名單姓名不同 |
| 狀態 | 待清點／待核對／已清點／已撤銷 |
| 金額 | 待清點留白；清點後輸入非負數字，不加貨幣文字 |
| 收件人員、收件時間 | 手機收件時保存；紙本或例外補登時人工填寫 |
| 清點人員、清點時間 | 清點人員填姓名；切換已清點後由觸發器補時間 |
| 備註 | 代送、多包、例外或更正原因 |
| 撤銷人員、撤銷時間 | 手機撤銷時保存，原收件資訊仍保留 |

人工清點先填署名、金額、清點人員，最後將狀態改為「已清點」。缺署名、清點人員或有效金額時，編輯觸發器會提示並改回待清點。只要已填金額（包含零元）或已有清點時間，手機就不允許撤銷；可用手機清點更正或 Sheet 管理。GiftDashboard 顯示待清點、待核對、已清點、已撤銷包數與已清點總額。

多包與名單外優先用手機「例外狀況／新增一包」取得 E 編號。管理者若手動新增列，不要複製既有內部ID或 E 編號；觸發器會補內部收件ID，但不會自動分配袋上 E 編號。代送保留原賓客關聯、填實際署名及備註，不更新到場狀態。

## 編輯紀錄與限制

- Gifts 保存手機收件／撤銷的人員與時間；重新收件不覆蓋舊列。
- GiftAudit 保存 Sheet 編輯範圍、帳號（若提供）、單格舊新值及編輯後列快照。清點人員欄需主動填寫，不能假設系統一定識別編輯者。
- Google 批次貼上不提供完整舊值，紀錄會明確標示；需要追查每次金額前後差異時請逐格編輯。多人快速同改一格的快照可能已包含後續修改。
- 原生 Sheet 編輯不受 Apps Script 的鎖阻擋。收件期間請使用篩選檢視查找，勿刪列、搬移欄位或重排整張 Gifts；避免兩人同時修改同一包，清點開始先填金額，手機再次查詢後會禁止撤銷。
- 刪除列、其他程式/API 寫入不屬編輯觸發器完整追蹤範圍；用已撤銷狀態保留歷史，不以刪列更正。觸發器未安裝或執行失敗時，不會自動補清點時間或產生編輯紀錄，需在 Apps Script 執行紀錄檢查。

上述平台限制參見 [Google 編輯事件文件](https://developers.google.com/apps-script/guides/triggers/events) 與 [可安裝觸發器文件](https://developers.google.com/apps-script/guides/triggers/installable)。

## 斷網備援

工作人員須先在有網路時完成登入並下載賓客快照。網路中斷後保持頁面開啟，QR、手動 ID、姓名及分類仍使用本機快照查詢；按「收到紅包」後看到「已保存在這支手機」即可繼續，主畫面會保留待同步紀錄。不要清除瀏覽器網站資料或更換瀏覽器。恢復網路後系統自動補送，也可按「立即重試」；逾時使用同一收件請求ID重送，後端不會因此建立第二包。

仍準備一張精簡紙本緊急表，欄位為：賓客編號、署名／姓名、收到紅包、經手人、收件時間、備註、補登完成記號。只有手機顯示本機儲存異常、頁面無法開啟、手機遺失／損壞或兩支手機都不可用時才改紙本；紅包仍寫賓客編號。恢復後由固定一人逐筆核對 Gifts 與兩支手機的同步面板，再補登紙本空缺。不要因逾時直接手動新增第二筆。

## 上線前驗收

### 查詢與收件耗時

2026-09-11 從開發電腦對舊部署進行唯讀測試：健康回應 1.39～2.10 秒；有效賓客查詢四次為 3.67、2.46、3.20、2.57 秒。測試未收件，這些數字不是手機端或優化後的實測值。

效能調整版本將 Guests 與 Gifts 各合併為一次資料讀取，唯讀查詢不取寫入鎖或 flush；收件／撤銷仍在鎖內重讀禮金資料並 flush。掃描保留相機串流，由既有閘門阻擋重複操作。

按「儲存並登入」時，同一次 session 回應會下載精簡賓客快照（賓客編號、顯示姓名、分類、桌號與當下紅包狀態），並與短期 session 一起保存在該分頁的 `sessionStorage`。每次 API 請求最多等待 20 秒；若 Apps Script 回應逾時或 JSONP 載入失敗，登入會自動重試一次，PIN、權限或後端明確拒絕則不會重試。之後 QR、手動 ID、姓名與分類查找直接使用本機快照，不等待 Apps Script。關閉分頁或 session 到期後快照會一併清除。這份狀態可能落後另一支手機；畫面會標示本機快照，而收件／撤銷必定由後端上鎖並重讀最新 Gifts，因此快照不會繞過重複收件或清點後禁止撤銷的保護。

登入時也會把後端建立的 session 與精簡賓客索引放入 Apps Script 短期快取。後續收件優先重用這兩份可信快取，省去 Script Properties 與 Guests 的固定讀取；快取遺失、超過大小限制或到期時會自動回到原本的 Properties／Sheets 驗證。Gifts 不使用快照決定是否可收件：每次收件仍在寫入鎖內重讀最新 Gifts 的固定帳本欄位、追加收件列並 flush，確保兩支手機同時操作時不會各新增一包；使用者額外加入的欄位或格式不會擴大每次收件的讀取範圍。

更新 `Code.gs`、`GiftRegister.gs` 並建立新的 Web App 部署版本，再更新前端即可套用，毋須重建工作表。成功回應包含 `serverMs`、`lockWaitMs`、`authMs`、`guestLookupMs`、`giftReadMs`、`giftWriteMs` 與 `flushMs`；結果視窗及瀏覽器的 `window.lastGiftTiming` 可區分整體後端、等鎖、工作階段驗證、賓客索引、禮金讀取、禮金寫入、確認寫入及其餘平台往返。診斷資料不含賓客、PIN、token 或金額。

以已登入狀態手動查同一賓客數次，比對總時間與後端時間。`totalMs - serverMs` 包含網路、平台啟動、序列化與重新導向等，不能全算成網路時間；session 往返另計。實際省下多少時間需部署後同裝置量測，不能以本機模擬測試宣稱。

新版部署的五次已登入唯讀查詢實測（同一開發電腦，2026-09-11）：

| 次數 | 總等待 ms | 後端 ms | 等鎖 ms | handler 以外 ms |
| --- | --- | --- | --- | --- |
| 1 | 2238 | 742 | 0 | 1496 |
| 2 | 4853 | 784 | 0 | 4069 |
| 3 | 2674 | 1143 | 0 | 1531 |
| 4 | 2464 | 1030 | 0 | 1434 |
| 5 | 3205 | 1854 | 0 | 1351 |

最慢一次的主要延遲在 handler 以外，未證實是哪一項平台或網路因素；這不是使用者手機端的量測。未執行收件寫入，不能以查詢時間代表收件時間。

前端新增結果視窗的「查看本次耗時」，可在手機查看操作總等待、登入、後端與等鎖時間；失敗或舊部署缺少後端數字時明確顯示未提供。此診斷資訊不包含賓客、PIN 或 token。

2026-09-12 手機首次查詢 `g001` 實測為總等待 5.64 秒，其中登入 2.02 秒、後端 1.60 秒、等鎖 0 秒，其餘 2.02 秒。這證實單筆資料量與鎖不是該次主要瓶頸；首次操作因 session 尚未建立而連續呼叫兩次 Apps Script。前端因此改為按「儲存並登入」時在單次登入回應同時取得賓客快照；設定完成後的查詢不再承擔 Apps Script 往返。正式手機速度仍須部署後實測，不能以本機單元測試宣稱確切毫秒數。

2026-09-16 以相同唯讀賓客查詢交錯測試 ContentService JSONP 與 HtmlService RPC 各六次：中位數分別為 1.92 秒與 1.62 秒，RPC 約快 0.30 秒（16%），但兩者仍有約一秒以上平台往返。因整體搬移 UI 的收益有限，保留 GitHub Pages 與 JSONP，改由本機收件佇列改善操作體感。

按「收到紅包」後先同步寫入瀏覽器本機儲存，成功即顯示「已保存在這支手機」並允許下一位；背景才呼叫 Apps Script。逾時或暫時失敗會保留相同請求編號重試，`RECEIVED` 或同請求的 `REPLAY` 才標成已同步；另一請求已先收件的 `ALREADY_RECEIVED` 標成待核對。這不是假裝已寫入 Sheet，畫面會持續區分本機保存與中央同步。

本機測試不代表正式部署已驗證。請在 Sheet 複本及實際兩支手機完成：查桌號不寫入、按收件後立即可下一位且稍後顯示已同步、斷網連收兩位並在恢復後補送、同步中重新整理後沿用同一請求編號、同賓客兩支手機撞單只有一筆且另一支顯示待核對、不同賓客都能成功、登入過期後由原人員續傳、撤銷與重新收件、已填金額或清點後拒絕撤銷、Sheet 單格更正出現 GiftAudit、手動多包不覆蓋，以及手機儲存失敗時不顯示成功。確認工作人員實際使用的 Google 帳號是否會出現在編輯事件中。

婚宴結束可停用 Web App。只更換 PIN 不會立刻使已核發的 session 失效（有效期最長八小時）。
