# 禮金簿操作與部署

## 初始化與升級

先備份 Sheet。Apps Script 需要同時放入根目錄的 `Code.gs` 與 `GiftRegister.gs`。在指令碼屬性設定 `API_PIN` 與 `SPREADSHEET_ID`，時區使用 `Asia/Taipei`。勿把 PIN 寫入公開程式碼。

執行 `setupSheet`：保留 Guests 舊到場資料，新增 Gifts、GiftAudit、GiftDashboard。舊 Dashboard 不會被覆蓋。Guests 若至少具備賓客ID與顯示姓名標題，可補齊舊欄位；自訂欄位會保留。Gifts 欄位若不符合預期順序則停止，不強行覆蓋禮金資料。現有報到資料不會轉成紅包收件。

名單編號若需補齊可執行 `generateGuestIds`，會避開已使用的編號。正式名單匯入格式另行確認，勿直接整段貼上來源 CSV 覆蓋 Guests。

由一位管理者執行 `installGiftEditTrigger` 並完成授權，安裝 `auditGiftEdit` 的可安裝編輯觸發器。同一帳號重跑不會重複安裝；不要由兩位管理者各安裝一份。程式/API 寫入不觸發 Sheet 編輯事件，收件與撤銷資訊直接保留在 Gifts 原始列。

更新 Web App 部署版本（執行身分為擁有者、允許現場裝置存取），接著更新 GitHub Pages 的 `/docs`。兩支手機重新整理、填 API URL、工作人員姓名與 PIN 後儲存。舊前端呼叫 checkin 會被拒絕，需重新整理新版。

## 手機接待

1. 掃 QR、輸入賓客編號或以姓名／分類查找。分類中的男方朋友、女方朋友均包含共同朋友。
2. 查看姓名、桌號、紅包狀態。只查桌號直接按「下一位」，不寫入到場或收件資料。
3. 收到紅包後按「收到紅包」。看到成功後，在紅包寫上畫面上的賓客編號。
4. 已收件者不會出現再次收件按鈕。尚未填金額／清點的收件可按「撤銷誤收件」，再次確認後撤銷。
5. 每次操作完成按「下一位」。掃描流程會恢復相機，查找流程可繼續搜尋。

兩支手機同時收同一賓客，一般流程只建立一筆有效收件。撤銷使用原收件ID，舊畫面不能撤銷之後重新建立的收件。回應逾時不自動重送；先重新查詢以確認實際寫入結果。

## Google Sheet 清點

在 Gifts 用賓客ID找實體紅包對應列。每列保留一個收件紀錄；撤銷不刪列，重新收件另增新列。內部收件ID不用寫到紅包上。

| 欄位 | 用法 |
| --- | --- |
| 收件ID、收件請求ID、撤銷請求ID | 系統追蹤用，勿修改或複製到新列 |
| 賓客ID、顯示姓名 | 對應主要送禮人 |
| 紅包署名 | 依紅包補登，允許與名單姓名不同 |
| 狀態 | 待清點／已清點／已撤銷 |
| 金額 | 待清點留白；清點後輸入非負數字，不加貨幣文字 |
| 收件人員、收件時間 | 手機收件時保存；紙本或例外補登時人工填寫 |
| 清點人員、清點時間 | 清點人員填姓名；切換已清點後由觸發器補時間 |
| 備註 | 代送、多包、例外或更正原因 |
| 撤銷人員、撤銷時間 | 手機撤銷時保存，原收件資訊仍保留 |

先填署名、金額、清點人員，最後將狀態改為「已清點」。缺署名、清點人員或有效金額時，編輯觸發器會提示並改回待清點。只要已填金額（包含零元）或已有清點時間，手機就不允許撤銷；更正改在 Sheet 完成。GiftDashboard 顯示待清點、已清點、已撤銷包數與已清點總額。

多包例外另新增一列，保留同一賓客ID及備註；名單外可暫留賓客ID空白、填署名與辨識備註。不要複製既有內部ID，觸發器會為手動列補收件ID。代送以紅包備註處理，不登記代送者為送禮人，也不更新到場狀態。

## 編輯紀錄與限制

- Gifts 保存手機收件／撤銷的人員與時間；重新收件不覆蓋舊列。
- GiftAudit 保存 Sheet 編輯範圍、帳號（若提供）、單格舊新值及編輯後列快照。清點人員欄需主動填寫，不能假設系統一定識別編輯者。
- Google 批次貼上不提供完整舊值，紀錄會明確標示；需要追查每次金額前後差異時請逐格編輯。多人快速同改一格的快照可能已包含後續修改。
- 原生 Sheet 編輯不受 Apps Script 的鎖阻擋。收件期間請使用篩選檢視查找，勿刪列、搬移欄位或重排整張 Gifts；避免兩人同時修改同一包，清點開始先填金額，手機再次查詢後會禁止撤銷。
- 刪除列、其他程式/API 寫入不屬編輯觸發器完整追蹤範圍；用已撤銷狀態保留歷史，不以刪列更正。觸發器未安裝或執行失敗時，不會自動補清點時間或產生編輯紀錄，需在 Apps Script 執行紀錄檢查。

上述平台限制參見 [Google 編輯事件文件](https://developers.google.com/apps-script/guides/triggers/events) 與 [可安裝觸發器文件](https://developers.google.com/apps-script/guides/triggers/installable)。

## 斷網備援

準備空白紙本，欄位為：賓客編號、署名／姓名、收到紅包、經手人、收件時間、備註、補登完成記號。正常時只使用數位紀錄，故障時改紙本；紅包仍寫賓客編號。編號不明者把紙本上的臨時備註一併寫在紅包上。

恢復後由固定一人逐筆核對 Gifts，確認沒有先前逾時但已成功的收件，再補登空缺，於紙本劃記完成。不要因逾時直接新增第二筆；無法確定時先保留紅包及紙本交叉核對。

## 上線前驗收

### 查詢與收件耗時

2026-09-11 從開發電腦對舊部署進行唯讀測試：健康回應 1.39～2.10 秒；有效賓客查詢四次為 3.67、2.46、3.20、2.57 秒。測試未收件，這些數字不是手機端或優化後的實測值。

效能調整版本將 Guests 與 Gifts 各合併為一次資料讀取，唯讀查詢不取寫入鎖或 flush；收件／撤銷仍在鎖內重讀禮金資料並 flush。資料仍即時讀取，沒有快取清點狀態。掃描保留相機串流，由既有閘門阻擋重複操作；手動 ID 使用相同後端優化。

更新 `GiftRegister.gs` 並建立新的 Web App 部署版本，再更新前端即可套用，毋須重建工作表。成功回應包含 `serverMs`（從禮金 API handler 開始至完成）與 `lockWaitMs`；瀏覽器的 `window.lastGiftTiming` 包含最近一次 API 的 `action`、`totalMs`、`serverMs`、`lockWaitMs`，不含賓客、PIN、token 或金額。

以已登入狀態手動查同一賓客数次，比對總時間與後端時間。`totalMs - serverMs` 包含網路、平台啟動、序列化與重新導向等，不能全算成網路時間；若是首次登入，session 往返另計。實際省下多少時間需部署後同裝置量測，不能以本機模擬測試宣稱。

本機測試不代表正式部署已驗證。請在 Sheet 複本及實際兩支手機完成：查桌號不寫入、同賓客同時收件只有一筆、不同賓客都能成功、撤銷與重新收件、已填金額或清點後拒絕撤銷、Sheet 單格更正出現 GiftAudit、手動多包不覆蓋、斷網及逾時後重新查詢核對。確認工作人員實際使用的 Google 帳號是否會出現在編輯事件中。

婚宴結束可停用 Web App。只更換 PIN 不會立刻使已核發的 session 失效（有效期最長八小時）。
