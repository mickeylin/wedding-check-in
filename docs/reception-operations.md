# 接待、喜餅與婚宴後清點

現場流程為取接待卡、掃碼或查姓名、確認分類與提醒、登記收到紅包，再按實體卡片的配色發餅。掃碼只開啟賓客資料。同行名單、備註、撤銷與例外紅包在「詳情與其他操作」。

## 名單與工作表

`Guests` 只保留八欄，前五欄與既有部署相容：賓客ID、顯示姓名、新郎/新娘方、桌號、備註、同行姓名、人數、喜餅共領ID。「新郎/新娘方」沿用既有欄名，值可為名單實際分類，例如麥當勞、湖畔咖啡。搜尋涵蓋顯示姓名、同行姓名、已確認舊稱與ID；分類選項由登入快照產生。

用 `CakeGroups` 的配額與 `Guests` 的喜餅共領 ID 核對印卡清單。

`Gifts`、`GiftAudit`、`GiftDashboard` 繼續使用。紅包收件先保存於裝置，再背景同步。

`scripts/prepare-reception-import.mjs` 是不連網的純轉換器。輸入 QR 清單、既有 Guests、既有 Gifts 與已確認的舊名對應，產生八欄名單、去重配額和卡號/賓客ID對照；拒絕配額不一致、重複ID、模糊對應，以及已被 Gifts 引用卻無新名單對應的ID。新ID避開所有舊ID。個資輸入與輸出放在被Git忽略的 `outputs/`，不要提交至公開儲存庫。

## 接待卡的喜餅配色

印卡配色草案如下。卡面可用色帶加盒數小字，QR code 維持白底。

| 卡片色帶 | 發放內容 |
| --- | --- |
| 淺綠 | 西式 1 盒 |
| 淺粉 | 西式 1 盒、中式 1 盒 |
| 白色 | 這張卡只用於接待 |

同一共領單位若有多張卡，只指定一張領餅代表卡。收禮人員發完餅後在卡上標記「已領」，再把卡還給賓客留存。配額空白、代領及超出上述盒數的情況先列入人工核對名單，再決定卡片標示。

## 例外紅包與回家清點

接待卡內可登記同組第二包、名單外及署名不同／代送；未在名單的送禮人可從主畫面入口進入。署名與已知備註先填，金額留白。這個例外入口需連線取得獨立E編號；成功前先把實體袋隔離，成功後立即寫上E編號。逾時沿用原請求重試，不能再按新增另一包。第二包需先讓第一包完成中央同步。

一般紅包仍寫賓客ID，多包使用各自E編號。紅包與喜餅共領ID不綁成一對一。未到場者代送紅包可獨立記錄，不自動推定出席或領餅。

「婚宴後使用」預設收合，內有「回家清點紅包」。編輯頁返回清單後，可在清單上方選「返回現場接待」。既有手機清點、署名、金額、待核對、更正歷程與安全重試保留，亦可在Sheet逐筆清點。具體規則見 `mobile-gift-counting.md`。

## 部署與驗收

1. 備份正式 Sheet 後，將 `Code.gs`、`GiftRegister.gs`、`CountGifts.gs` 放入 Apps Script。從舊版升級時移除專案中的 `Reception.gs`。
2. 初次安裝時執行 `setupSheet`，確認 Guests 前七欄。若 F:G 有自訂欄，先備份移開。從舊版升級可沿用既有的 PIN、試算表與 Web App 網址。
3. 更新 Web App 部署版本，再發布 `docs/` 前端。工作人員重新登入下載最新名單。
4. QR內容使用正式賓客ID，不使用QR001等排版卡號。既有已被紅包引用的ID不可改配別人。名單更動或重排後不可重新分配已使用的共領ID。
5. 驗收同行姓名查詢、掃碼收件、離線收件同步、第二包 E 編號、婚宴後清點及返回現場接待。印卡前逐一核對共領代表卡與卡片色帶。

前端使用固定的 Apps Script 網址，工作人員只需填姓名與 PIN。

賓客編號以 `PM01` 到 `PMFF` 表示，將原十進位數值轉成兩位十六進位，例如 `G010` 對應 `PM0A`。先部署 Apps Script 與前端，驗證舊 QR 和新編號皆能查到同一位，再更新正式 Guests A 欄和「簽到QR Code清單」的系統賓客編號。歷史紅包與稽核紀錄保留原值，程式查詢時會辨識兩種編號。

部署新版 Apps Script 並驗證登入、收件及清點後，即可移除舊的 `CakeLog` 工作表。印卡仍使用 `CakeGroups` 和喜餅共領 ID。
