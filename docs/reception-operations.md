# 接待、喜餅與婚宴後清點

現場流程：取接待卡 → 工作人員掃碼／查姓名 → 看同行者、桌號與提醒 → 分別確認收到紅包與發放喜餅 → 下一位。掃碼不自動收紅包、發餅或登記整組到場，不輸入實到人數。

賓客頁預設只顯示姓名、桌號、紅包標記、本組人數、重要提醒與本次可領喜餅；主要按鈕為「收到紅包」「發放喜餅」「下一位」。同行名單、完整備註、調整盒數、配額明細、更新領餅狀態、撤銷與例外紅包入口收在「詳情與其他操作」。發餅仍須確認摘要，領完隱藏發放按鈕，未知配額與待核對不隱藏為一般成功。

## 名單與工作表

`Guests` 只保留八欄，前五欄與既有部署相容：賓客ID、顯示姓名、新郎/新娘方、桌號、備註、同行姓名、人數、喜餅共領ID。「新郎/新娘方」沿用既有欄名，值可為名單實際分類，例如麥當勞、湖畔咖啡。搜尋涵蓋顯示姓名、同行姓名、已確認舊稱與ID；分類選項由登入快照產生。

`CakeGroups` 每個共領ID只放一列：喜餅共領ID、共領名稱、西式配額、中式配額。配額空白表示未確認，不當作0；未知品項不可發放，其他已確認品項可以先領。不要在正在接待時手動修改配額、刪改發放紀錄或重新編共領ID。

`CakeLog` 是新增式發放帳本，保留發放ID、共領ID、接待卡賓客ID、動作、兩種盒數、經手人、時間、請求ID、原發放ID與更正原因。發放與撤銷都新增一筆，不刪原列。多張卡共領一份時，系統按同一共領ID加總有效發放，後端鎖內再次核對，不能超領。

`Gifts`、`GiftAudit`、`GiftDashboard` 繼續使用。紅包收件維持裝置先保存、背景同步；這不套用於喜餅發放。

`scripts/prepare-reception-import.mjs` 是不連網的純轉換器。輸入 QR 清單、既有 Guests、既有 Gifts 與已確認的舊名對應，產生八欄名單、去重配額和卡號/賓客ID對照；拒絕配額不一致、重複ID、模糊對應，以及已被 Gifts 引用卻無新名單對應的ID。新ID避開所有舊ID。個資輸入與輸出放在被Git忽略的 `outputs/`，不要提交至公開儲存庫。

## 喜餅操作

1. 掃卡後顯示該共領單位的配額、已領和剩餘盒數。顯示成員與桌號不等待喜餅查詢。同一家同時查詢只送一個請求；10秒內換掃同家的卡可沿用記憶體中的狀態，標示「上次狀態」。較舊資料先顯示並在背景更新；「更新領餅狀態」可強制重新查詢。這份暫存不跨API、操作人員或登入階段，也不保存到裝置儲存空間。
2. 輸入本次西式／中式盒數，可只領一種。按確認後等待伺服器成功，再將喜餅交給賓客。
3. 確認成功後會顯示這次應交付盒數；不要只憑快照或取下卡片判定已領。
4. 更正使用指定原發放ID，先核對喜餅確實未交付或已收回，再填原因撤銷。撤銷不代表實體自動收回；需要正確登記時重新輸入實際盒數。
5. 逾時或網路失敗時，本機保留原內容與請求ID，禁止建立另一筆發放。恢復後由原操作人員按「核對原操作結果／重試」。若先前已成功，重試不再扣配額；請先核對實體是否已交付，不可因看到重試成功再拿一份。
6. 待核對操作不可換API或換操作人員續送。每位工作人員只使用一個分頁，不清除網站資料。

離線時喜餅按鈕停用，改由固定一人使用同一份紙本記錄，避免兩份獨立紙本各發一次。已經有結果未明的線上操作先隔離處理，不因切紙本而重新發一次。復線後先核對原操作，再由固定人員逐筆補登空缺；補登成功不代表再交付一次。

目前未提供代領專用配額操作。名單備註中的額外代領份數（例如替未出席者帶餅）需另核對，不併入代領者自己的配額，也不能透過更正任意增加份數。

## 例外紅包與回家清點

接待卡內可登記同組第二包、名單外及署名不同／代送；未在名單的送禮人可從主畫面入口進入。署名與已知備註先填，金額留白。這個例外入口需連線取得獨立E編號；成功前先把實體袋隔離，成功後立即寫上E編號。逾時沿用原請求重試，不能再按新增另一包。第二包需先讓第一包完成中央同步。

一般紅包仍寫賓客ID，多包使用各自E編號。紅包與喜餅共領ID不綁成一對一。未到場者代送紅包可獨立記錄，不自動推定出席或領餅。

「婚宴後使用」預設收合，內有「回家清點紅包」。既有手機清點、署名、金額、待核對、更正歷程與安全重試保留，亦可在Sheet逐筆清點。具體規則見 `mobile-gift-counting.md`。

## 部署與驗收

1. 備份正式Sheet，暫停接待。四份Apps Script來源須一起更新：`Code.gs`、`GiftRegister.gs`、`CountGifts.gs`、新增的 `Reception.gs`。
2. 執行 `setupSheet`，確認Guests前八欄與CakeGroups、CakeLog欄序；若F:H有自訂欄則停止，先備份移開。沿用原API_PIN、SPREADSHEET_ID與原Web App網址，不在公開程式碼存PIN。
3. 更新Web App部署版本，再發布 `docs/` 前端，工作人員重新登入下載最新名單。新版快取使用V2鍵，不沿用舊的五欄賓客快取。
4. QR內容使用正式賓客ID，不使用QR001等排版卡號。既有已被紅包引用的ID不可改配別人。名單更動或重排後不可重新分配已使用的共領ID。
5. 在Sheet複本與兩支實際手機驗證：同行者姓名可找到同卡、只查詢不寫入、不同卡共領只發一次、西式先領後補中式、配額未確認拒絕該品項、同時發放只有配額內成功、逾時/重整重試不重複、換人重試被攔、發放更正、一般紅包離線佇列、第二包E編號與婚宴後清點。

2026-10-29 共領查詢加速：若已完成上述初次部署，只需更新 `GiftRegister.gs` 與 `Reception.gs`、更新既有Web App部署版本，再重新登入；不需重新執行setupSheet或改Sheet欄位。登入時會一併取得全部共領狀態，掃卡可先顯示該快照；發餅仍在後端鎖內重新讀取名單、配額及帳本，成功後才交付。新前端也相容尚未更新的後端，仍可合併重複查詢及短暫沿用同家狀態。

自動測試確認單次狀態查詢的帳本讀取由兩次減至一次，同家同時查詢的API請求由兩次減至一次；另涵蓋快照過期、強制更新及舊回應不覆蓋已成功發放結果。這些是請求次數與正確性驗證，尚未量測正式手機的實際等待秒數。
